# 提交前的密文检查

工作电脑上的磁盘做了透明加密（亿赛通）。在没被授权的进程里，读到的文件内容是密文；那样提交上去的文件，GitHub 上是乱码，AI 读不了，人也读不了。

这个工具就干一件事：**判断要提交的内容是不是可读文本**，不是就拦住。

## 怎么跑

```bash
node tools/check-plaintext.mjs             # 检查暂存区，默认
node tools/check-plaintext.mjs --all       # 检查全部已跟踪文件
node tools/check-plaintext.mjs a.md b.md   # 检查指定文件
node tools/check-plaintext.mjs --fingerprint  # 额外打印头 32 字节，用来补指纹
```

通过退出码 0，不通过退出码 1。

## 为什么检查"暂存区"而不是"磁盘上的文件"

这是整个工具最关键的一点。

磁盘上的文件是谁读到的，取决于是哪个进程在读。如果 node 被加密软件授权、git 没有，就会出现一种很坏的情况：**你手动看文件是明文，提交上去却是密文**。反过来也一样。

暂存区（git 索引里那份）才是**真正会被推上 GitHub 的字节**。检查它，等于检查了答案本身，不用去猜哪个进程被授权了。

`git commit` 之前，`git show :路径` 拿到的就是这一份。

## 装上钩子，自动拦

在仓库根目录跑一次：

```bash
git config core.hooksPath .githooks
```

之后每次 `git commit`，钩子会先跑检查。有密文就打印原因并取消提交。

撤销：`git config --unset core.hooksPath`。
硬跳过（确认误报才用）：`git commit --no-verify`。

## 云端兜底

`.github/workflows/text-guard.yml` 在每次推送到 main 后跑一遍全量检查。它的作用是**事后提醒**——如果本地钩子没装或跳过了，密文已经进了仓库，这次 CI 会变红，GitHub 会发邮件。

它拦不住提交，只能告诉你有事。真正拦住的是本地钩子。

## 判据

按顺序，命中任意一条就判失败：

1. 命中已知加密指纹（目前为空，见下）
2. 含 `0x00` 空字节
3. 整份不是合法 UTF-8
4. 控制字符占比超过 1%
5. 熵超过 7.4（正常文本 4~6.5，加密或压缩数据 7.9 以上）
6. `.md` / `.txt` 超过 1KB 却整份没有换行符

只检查文本类扩展名（md、json、yaml、js、py、kt、java 等），图片二进制一律跳过。

## 指纹还没补

亿赛通的加密文件头是固定字节，命中它是最干脆的判据——比熵和 UTF-8 都准。但我手上没有一份确认的密文样本，所以指纹表 `KNOWN_HEADERS` 现在是空的，全靠上面第 2~6 条兜着。

补齐的办法：在**会产生密文的那台电脑**上，拿一个已知会被加密的文件，跑

```bash
node tools/check-plaintext.mjs --fingerprint 那个文件
```

把它打印出来的头 32 字节，加进脚本里的 `KNOWN_HEADERS`：

```js
const KNOWN_HEADERS = [
  { hex: '把这里换成实际的头字节', note: '亿赛通' }
];
```

补上之后，误报率和漏报率都会明显下降。

## 这个工具管不了的

- **内容敏感不敏感**。它只判断"是不是可读文本"，读得懂的公司代码照样能通过。这一层得靠人工和 AGENTS.md 里的规则。
- **已经在历史里的密文**。它只看当前这次提交。要清历史得重写 commit，那是另一件事。
