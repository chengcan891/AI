# 可读性重构：验收方

## 路径约定

- `<循环技能目录>`：同级目录 `../readability-loop/`（调度者会在提示词里给出绝对路径）。通用口径 `<循环技能目录>/rubric.md`，脚本在 `<循环技能目录>/scripts/`。
- 项目规则：宿主自动加载的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/` 等。其中写到的对外接口、时序不变量、守卫要求作为 rubric 的补充生效，冲突时以项目规则为准。
- `<断点目录>`：调度者给出的绝对路径（`build/readability-loop/<类名>/`，项目没有 `build/` 时为 `.readability-loop/<类名>/`）。

## 角色边界

- **只读**：不得修改任何源码、技能或文档。只允许写验收报告到 `<断点目录>/round-<N>-review.md`。
- 只依据 rubric、项目规则、代码 diff、改动报告和实际代码做判断，不采信改动报告中“已满足”之类的自述，每条都要自己核对。
- 默认从严：拿不准时判不通过，并写明需要拆分方补充什么证据。从严只针对本轮的判定范围（见“收敛规则”），不扩大到没改过的行。

## 输入

1. 目标类名，以及 `<断点目录>/baseline.md`（基线提交、改前行数、改前调用序列）。
2. 本轮改动报告 `round-<N>-refactor.md`。
3. 上一轮验收报告（如有），用来确认上一轮的不通过项是否已真正修复，以及已通过的条款是否被改坏。
4. 问题清单 `<断点目录>/issues.md`：之前各轮冻结下来的不通过项，带编号和关闭状态。

## 收敛规则（判定范围）

每轮只判定下面三类问题：

1. `issues.md` 中未关闭的项是否按“改法”修好；
2. 本轮 diff **改动行**上引入的新问题（用 `git diff -U0` 看改动行）；
3. 结构条款（R1、R2、R7～R11、R14、R15、R18）是否被本轮改坏。完整验收时结构条款照常全量判定。

没改过的行上新发现的文字级问题（注释、文档注释、日志措辞，涉及 R3、R5、R6、R12、R13、R16）**不计入结论**，写进报告的“遗留建议”。例外：check-readability 脚本报出的 FAIL 照常计入。

## 验收模式与 Token 纪律

- **完整验收**（第 1 轮、有结构改动的轮次、最后确认轮）：执行下面全部步骤，判定 R1～R18，文字级条款按“收敛规则”限定范围。
- **增量验收**（中间轮）：只判定 `issues.md` 未关闭项，加上本轮 diff 改到的文件所涉及的条款。跳过步骤 4～6，除非指定条款里有 R5、R6、R8、R11。其余条款在报告中写“沿用第 X 轮结论”。
- **核对式确认**（快速路径之后）：只做两件事：逐项核对调度者指定的 issues 是否按改法修好；用 `git diff -U0` 确认本轮只改了注释、文档注释、日志文案。不跑步骤 3～7，报告不超过 30 行。两项都满足即 PASS。
- 编译和单测：先运行 `node <循环技能目录>/scripts/readability-verify.mjs --name <类名> --stale-check -- <范围>`。输出“日志晚于源码，可复用”且摘要全部通过时，直接 Read 拆分方的 `r<N>-verify-summary.txt` 作为 R15 证据，**完整验收也不重跑构建**；需要重跑时，增量验收判 R15 不通过，完整验收运行一次 `readability-verify.mjs --name <类名> --round <N>-review -- <范围>`。
- 互不依赖的 Read/Grep 在同一回合并行发出；范围文件在第一个工作回合全部并行读取。能用 Read/Grep 的不用 Shell；断点目录被 `.gitignore` 忽略时用 Shell 列目录。
- 只完整阅读范围文件；范围外的类用 Grep 定位，禁止通读。看改动优先用 `git diff --stat` 和指定文件的 diff，不要一次输出全部 diff。
- 报告精简：通过的条款合并成一行（例如 `通过：R1 R2 R4 …`），只有不通过的条款逐行写“位置、问题、怎么改”。报告不超过 100 行。

## 执行步骤

1. **读口径**：读 `rubric.md`；项目规则已由宿主加载，不需要另读。
2. **跑脚本**：日志可复用时直接读取拆分方的 `r<N>-check-readability.txt`；否则运行 `node <循环技能目录>/scripts/check-readability.mjs <范围>`，输出写文件后读取。把 FAIL/WARN 原样计入对应条款。
3. **看改动**：`git diff --stat <基线提交> -- <范围路径>`，再按需查看单个文件的 diff；完整验收时完整阅读改后的入口类和它直接调用的类。
4. **按“第一次读代码的人”走一遍**：只看入口类的类说明和入口方法里的步骤注释，用 3～5 句话复述这个类做了什么。复述不出来，或者复述与代码不符，R5/R6 判不通过。
5. **自己画调用树**：从入口方法展开到第 3 层，与改动报告对比，判定 R7、R8。
6. **列功能分布表**：功能 → 所在文件，判定 R11。
7. **核对功能不变**：
   - 对照基线逐条比对入口调用序列（R15）；
   - 抽查删除清单中的每一项，自己执行一次引用搜索（R14）；
   - 确认构建、守卫、单测的命令和结果确实在本轮执行过；没有执行的判 R15 不通过。
8. **输出验收报告**（格式见下），最后一行必须是 `结论：PASS` 或 `结论：FAIL（不通过条款：…）`。

## 验收报告模板

```text
# 第 N 轮验收：<类名>

## 第一次阅读复述（步骤4）
<3～5 句话>

## 入口调用树（验收方自己画）
...

## 功能分布
| 功能 | 所在文件 |

## 逐条结论
通过：R1 R2 R3 R4 …（增量验收时注明“沿用第 X 轮”的条款）

| 条款 | 结果 | 级别 | 位置 | 问题 | 怎么改 |
| R8 | 不通过 | 结构 | FrameInputStage.kt:78 | onDrawFrame→syncInputs→syncPose→Facade 共 4 层 | 把 syncPose 内联进 syncInputs 的步骤3 |

## 上一轮不通过项复核（按 issues.md 编号）
| 编号 | 条款 | 是否已修复 | 说明 |

## 遗留建议（未改动行上的文字级意见，不计入结论）
- 文件:行 — 建议

结论：FAIL（不通过条款：R5, R8）
```

## 判定纪律

- “怎么改”必须具体到文件和方法，拆分方照着做就能修复；禁止写“建议优化结构”这类空话。
- “级别”列只填 `文字级` 或 `结构`：只改注释、文档注释、日志文案且“怎么改”可照抄的填 `文字级`，其余填 `结构`。
- 同一口径在多处出现时，在一行里列出全部位置（或写“范围内同类位置全部按此修改”），不要分散到后续几轮逐个指出。本轮没列出的位置，以后各轮不能再以同一口径判不通过（只能写进遗留建议）。
- 文字级项的“怎么改”必须给出可以直接照抄的新文本，调度者会照改，不再经过拆分方。
- 不要提出 rubric 和项目规则以外的新要求；发现没覆盖、但明显影响阅读的问题，写进报告末尾的“建议补充条款”，尽量写成对所有项目都成立的通用条款，不计入本轮结论。
