# 可读性重构验收清单（通用口径，拆分方与验收方共用）

本清单是“结构分明、容易阅读、功能不变”的通用判定口径。拆分方按它改，验收方按它判；两边不得各自补充口径。

“项目规则”指宿主自动加载的项目规则文件（`AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`，以及其中标为强制的规范技能）。项目规则里写到的对外接口、时序不变量、守卫脚本、业务术语，作为本清单的补充生效；与本清单冲突时以项目规则为准。本循环不要求项目另建任何配置文件。

用户对通过验收的结果仍不满意时，优先把要求改写成对所有项目都成立的条款补进本文件；确实只与某个项目有关的（模块名、业务术语），写进该项目已有的规则文件。不要在对话里临时口头约定。

## 条款设计目标

| 读者痛点 | 对应条款 |
|---|---|
| 类还是比较大 | R1、R2 |
| 方法内部缺少步骤说明 | R5、R6 |
| 类的职责不够明确 | R3、R4 |
| 拆完后一个方法调用跳来跳去，无法阅读 | R7、R8、R9、R10、R11 |
| 拆出的类都平铺在同一个包/目录里 | R18 |
| 成员变量没有说明 | R16 |
| 没有调用方的统计、打印代码仍然保留 | R17 |
| 前提：功能不变 | R14、R15 |

判定方式：`[脚本]` 由 `scripts/check-readability.mjs` 判定（当前内置 Kotlin 词法检查，其它语言按人工判定）；`[人工]` 由验收方阅读代码判定。
下文阈值（行数、嵌套层数、包内文件数等）与脚本一致，对所有项目相同。
所有条款都是必须项，任一不通过即整体 FAIL。确实无法满足时，必须在类说明里写明“例外原因 + 退出条件”，验收方认可后才算通过。

“文档注释”指该语言的文档注释（KDoc、Javadoc、JSDoc、Python docstring、C# XML 注释等）。

## A. 体量

- **R1 文件体量 [脚本]**：单文件 ≤ 300 **代码行**（不含注释、文档注释、空行和多行原始字符串，例如 shader、SQL 模板），超过即不通过。禁止为了压低行数把同一功能拆到额外文件，导致违反 R8 或 R11。
- **R2 总量不膨胀 [人工]**：拆分后目标类及其拆出类的**代码行数**（不含注释和空行）合计，不得超过拆分前的 110%。拆分的结果是“把东西放对位置并删掉冗余”，不是“同样的代码加更多壳”。报告必须给出拆分前后的代码行数和物理行数。
  - 注释和说明不计入上限。禁止为了凑行数压缩代码，例如把多参数挤成一行、把访问器合并到属性行、把必要的文档注释改成行尾注释。发现这类压缩按 R2 判不通过。

## B. 类职责

- **R3 类说明三段式 [脚本 + 人工]**：每个类的文档注释必须包含以下三段，且用业务语言书写：
  - `职责：` 一句话（≤ 40 字），说清“本类负责什么”；
  - `不负责：` 列出最容易被误以为属于本类、实际在别处的 1～3 件事，并写出在哪个类；
  - `使用步骤：` 编号列出外部如何使用本类（构造 → 生命周期回调 → 周期性调用 → 释放）。
  脚本检查三个标签是否存在；人工检查内容是否真实、是否和代码一致。
  只承载数据、没有方法的类（快照、配置、值对象）只需一句话说明用途。
- **R4 类名可解释 [人工]**：类名必须能直接对应 `职责：` 那句话。禁止只靠 `Stage` / `Coordinator` / `Manager` / `Helper` / `Facade` / `Workspace` / `Util` 这类通用后缀表达职责；有这类后缀时，前缀必须说明“管什么”。
  - 方法体量 [脚本]：单个方法 ≤ 40 行；花括号嵌套（含 lambda）超过 3 层给 WARN。脚本以 R4 编号报告。

## C. 方法内部可读性

- **R5 步骤注释 [脚本 + 人工]**：方法体有 ≥ 4 条语句时，必须用 `// 步骤N：做什么（为什么）`（按语言换成对应的行注释符）标出步骤，编号从 1 连续递增。
  - 每个步骤注释覆盖紧随其后的一条或多条语句，直到下一个步骤注释；
  - 写“做什么 + 为什么”，用业务语言，例如 `// 步骤2：先同步车辆位姿，相机要跟随这一帧的车辆位置`；
  - 步骤覆盖的每条语句都要在注释中交代作用，包括计时、清零、记录旧值、复用列表清空等辅助语句；后续步骤会用到的值，要写明给哪一步用；
  - “为什么”必须写在步骤注释里，不能只写在文档注释里；
  - 禁止只把方法名翻译成中文，例如 `// 步骤2：同步位姿`。
- **R6 文档注释与方法体一致 [人工]**：文档注释里如果写了“执行顺序 1、2、3…”，必须与方法体内的步骤注释一一对应（数量、顺序、含义都一致）。不一致时以方法体为准修改文档注释。

## D. 结构与阅读路径

- **R7 禁止空壳转发 [脚本 + 人工]**：以下情况必须内联回调用处，并在调用处用步骤注释说明：
  - 私有方法体只有一条语句，且在本文件内只被调用 1 次；
  - 类只有一个对外方法，且该方法只是把参数转给另一个对象（转发类），并且少于 40 行代码；
  - 例外：该方法被 ≥ 2 处调用；或它封装了 `try/finally`、加锁、资源/图形状态保存与恢复这类必须成对出现的逻辑。
- **R8 调用深度 [人工]**：从入口方法到真正做事的代码，**跨文件跳转 ≤ 3 层**。验收方必须在报告里画出入口调用树（展开到第 3 层），并标出超过 3 层的链路。
- **R9 数据流显式 [人工]**：
  - 阶段之间的数据通过参数和返回值传递；同一份数据禁止既作为返回值传递、又写进全局或共享对象（双通道）。确实需要共享工作区时，工作区的每个字段必须注明“由哪个方法写、由哪些方法读”；
  - 隐式接收者作用域（Kotlin `with(x) {}`、JS `with`、Python 大量 `self.` 之外的隐式全局等）会让读者看不出字段从哪来。跨类读取工作区字段的方法里禁止使用，改为显式写 `work.xxx`。
- **R10 状态唯一 [脚本 + 人工]**：同一状态只保存在一个地方（例如画面宽高只能由一个类持有，其他类通过参数获得）。脚本报告同名私有可变字段出现在 ≥ 3 个文件中的情况，由人工判定是否属于重复状态。
- **R11 按功能聚合 [人工]**：同一个功能的逻辑不应散落在 3 个以上的类里。验收方需列出“功能 → 所在文件”表，散落超过 3 个类的，必须说明原因或合并。
- **R18 按功能分包 [脚本 + 人工]**：拆分出的类不得全部平铺在入口类所在的包（目录）里，能按功能分子包的必须分子包。每次可读性重构都要检查，不分包时在报告里写明原因。
  - 触发条件：同一包内同一功能的类 ≥ 3 个（同前缀或同后缀一组），或包内主源文件 > 8 个。脚本给出 WARN 和分组建议，是否分包由人工判定。
  - 分包依据：按业务功能或流程阶段分，子包名用小写英文名词并在入口类说明中解释；禁止按技术类型分（`util`、`model`、`impl`、`helper`、`base`）。
  - 粒度：每个子包至少 2 个类；单个类不单独建子包。入口类（被包外调用的类）留在父包，子包放它调用的实现类。
  - 依赖方向：父包入口类可以依赖子包；子包可以依赖父包中的共享数据类型；两个子包之间禁止双向依赖。出现时把共享类型上移到父包，或合并两个子包。
  - 功能不变：被其他模块（例如其它 Gradle 模块、其它 npm 包）引用的类不迁移包名（属于 R15 对外签名）；迁移时同步修改测试包路径、所有导入语句、文档注释链接、技能和现行文档中的全限定名，并按 R14 给出迁移后的全仓库引用搜索证据（旧全限定名 0 处未标注引用）。
  - 验收方在报告里给出“包 → 类 → 一句话职责”表和子包间依赖方向。

## D2. 成员与死代码

- **R16 成员说明 [脚本 + 人工]**：类中每个成员属性（构造参数属性、私有字段、延迟初始化字段、类常量）都必须有紧邻的文档注释，用一句业务语言说明：
  - 它是什么、存什么（单位、坐标空间、取值含义）；
  - 由谁写入、被谁读取（对组件型成员，写“负责什么、本类在哪个步骤调用它”）；
  - 生命周期：何时创建、何时重置/清除。
  - 禁止只把变量名翻译成中文，例如 `/** 计划解析器。 */`。
  - 一组同义的常量可共用一条分组说明，但每个常量仍需行尾说明含义。
  - 数据类、值对象的构造字段可以改用类文档注释中的 `@property`/`@param` 集中说明。
- **R17 删除无调用的统计与打印 [人工]**：统计查询方法、计数器字段、诊断/打印方法，如果在全仓库（源码、测试、工具）都没有调用方，必须删除，并连带删除只为它服务的计数器、字段和格式化代码。
  - 判断依据是全仓库引用搜索，不能只搜本文件；被测试调用的保留；
  - 统计、调试类接口默认由程序内部控制：仓库内没有调用方时，连同公共调试接口及其数据类一起删除，并同步更新提到它们的文档，不需要再单独询问用户；项目规则声明调试接口对外承诺的除外；
  - 业务功能类的对外 API（SDK/库 public API）仍不得删除，能经由它到达的在报告里列出调用链；
  - 只被日志使用、日志本身又在高频路径无条件输出的，按 R12 处理；
  - 删除清单同样要满足 R14 的引用证据要求。

## E. 日志与注释

- **R12 日志位置 [脚本 + 人工]**：
  - 生命周期方法、低频状态变化方法可以打 info 日志；
  - 高频路径（渲染循环 `onDrawFrame`/`draw*`/`render*Frame`、`advance*`/`synchronize*`/`prepareFrame*`、游戏 `tick*`/`onUpdate`，以及项目规则指出的其它热路径；脚本按方法名自动识别前几类）禁止无条件打日志，只允许限频、只在状态变化时打，或只在异常分支打；
  - “属性日志”只在属性值发生变化时打，并带上旧值和新值。
- **R13 注释无黑话 [人工]**：英文术语或内部简称首次出现时，必须写成“术语（中文解释）”。禁止出现未解释的内部简称。注释描述代码现在做什么、为什么这样做，禁止写“本次把 X 移到 Y”这类重构过程描述。

## F. 功能不变（硬门槛）

- **R14 删除有证据 [人工]**：每个被删除或改名的方法、字段，报告里必须附上全仓库引用搜索结果（0 处引用），并确认它不是对外 API、反射/JNI/序列化入口或配置文件引用的入口。
  - 历史分析、审查记录类文档（标题或文件名表明是分析、评审、排查记录，例如 `*-analysis.md`、`*-review.md`）允许保留旧标识符，但每处必须紧跟“已迁移至 `新类.新成员`”标注；未标注视为不通过。
  - 源码、测试、技能文件和现行使用/阅读指南仍要求 0 处引用。
  - 验收报告中把命中分为“带标注的历史引用（允许）”和“未处理引用（不通过）”两类分别列出。
- **R15 行为等价 [人工 + 编译]**：
  - 对外签名（被其他模块使用的部分）不变；
  - 入口方法的实际调用序列与拆分前一致：报告中给出“拆分前调用序列 / 拆分后调用序列”对照表，逐条对齐；
  - 线程边界、资源/图形状态设置顺序、处理阶段（如绘制 Pass）顺序、关键状态的读取时机，以及项目规则写明的时序不变量不变；
  - 不新增高频路径的对象分配，不新增重复遍历；
  - 编译、单测、项目规则要求的守卫由 `readability-verify.mjs` 一次跑完，且确实在本轮执行过。摘要写“未识别构建系统/单测命令，已跳过”时不判不通过，但项目规则写有编译命令的，必须用 `--build` 执行。

## 验收结论格式

验收方必须逐条输出，不允许只写总结：

```text
R1  通过 | 不通过  文件:行号  问题  怎么改
...
结论：PASS / FAIL（不通过条款：R5, R8）
```
