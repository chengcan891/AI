# 可读性重构循环（调度者）

对用户在命令后给出的目标类执行可读性重构，循环直到验收通过再交付。你是调度者：除“文字级快速路径”外**不要自己改代码，也不要自己验收**，只负责启动子代理、维护断点文件、控制轮数、耗时和 token 消耗。

## 路径约定

- `<技能目录>`：本 SKILL.md 所在目录。拆分方、验收方技能在同级目录 `readability-refactor/`、`readability-review/`。启动子代理前，把这三个目录解析成**绝对路径**写进提示词（子代理不知道技能装在哪里）。
- 通用口径：`<技能目录>/rubric.md`。项目适配：项目规则（宿主自动加载的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/` 等），不需要也不读取任何专用配置文件。
- 脚本：`node <技能目录>/scripts/readability-verify.mjs` 与 `node <技能目录>/scripts/check-readability.mjs`，在项目根目录执行。构建系统自动识别（Gradle / Maven / Node / Cargo / Go / dotnet / Python）；识别不准时用 `--build "<命令>"`、`--test "<命令>"` 覆盖；识别不到时记为“已跳过”，不算失败。
- 断点目录：项目有 `build/` 时为 `build/readability-loop/<类名>/`，否则为 `.readability-loop/<类名>/`（脚本自动写 `.gitignore`，不进版本控制）。下文简写为 `<断点目录>`。
- 旧断点里记录的验证命令（例如项目内 `tools/readability-verify.mjs`）一律改用本技能的脚本。

## 断点文件（中断后只靠它们续跑）

熔断、关会话、手动中止后，新会话只读这些文件续跑，**禁止翻聊天记录找进度**，也禁止相信交接文字里的“还剩几处”，一律以文件和源码为准。

| 文件 | 谁写 | 内容 |
|---|---|---|
| `loop-state.md` | 调度者 | 累计轮次、阶段、下一步、范围文件、用户确认的轮次上限、守卫参数 |
| `issues.md` | 调度者 | 冻结的问题清单（见“收敛规则”），每项有编号和“未关闭/已关闭” |
| `r<N>-todo.md` | 拆分方（快速路径时由调度者写） | 本轮全部待改项，一项一行：`- [ ] 文件:方法 ｜ 定位文本 ｜ 改法`；**每改完一个文件立刻勾选该文件的项** |
| `r<N>-verify-summary.txt` | readability-verify | 本轮校验摘要 |
| `round-<N>-refactor.md` | 拆分方（快速路径时由调度者写） | 本轮改动报告 |
| `round-<N>-review.md` | 验收方 | 验收报告 |

`loop-state.md` 模板（调度者新建，之后只改“阶段”“下一步”两行）：

```text
# 可读性循环断点：<类名>
累计轮次：<N>
阶段：<待办 / 编辑 / 校验 / 报告 / 验收 / 判定 / 交付 / 交接>
下一步：<一句话，新会话照做即可>
用户确认的累计轮次上限：<6 或用户确认后的数字>
本轮结构改动：<有（说明）/ 无>
守卫参数：<例如 --guard "node tools/check-x-guard.mjs"，或“无”>
范围文件：<列表>
待办：r<N>-todo.md    校验：r<N>-verify-summary.txt    报告：round-<N>-refactor.md / round-<N>-review.md
```

| 阶段 | 判定依据 | 下一步 |
|---|---|---|
| 待办 | 没有 `r<N>-todo.md` | 启动拆分方，先写 todo 再动手 |
| 编辑 | todo 里还有 `[ ]` | 启动拆分方续跑（或快速路径由调度者照改），只做未勾选项 |
| 校验 | todo 全部 `[x]`，没有通过的 verify 摘要 | 跑一次 verify |
| 报告 | verify 通过，没有 `round-<N>-refactor.md` | 写改动报告 |
| 验收 | 有改动报告，没有 `round-<N>-review.md` | 启动验收方 |
| 判定 | 有验收报告 | 按 1.3 判定 |

更新时机：启动任何子代理**之前**、子代理返回**之后**各更新一次。子代理因熔断中途返回时，调度者先 Grep todo 中的 `[ ]` 数、把阶段改成实际阶段，再结束本轮回复。

## 收敛规则（防止轮数失控）

轮数失控的主要原因是验收方每轮都在**没改过的行**上挑出新的同类文字问题。以下规则对调度者和验收方都生效：

1. **问题清单冻结**：每次验收 FAIL 后，调度者把“不通过条款”表的每一行追加进 `issues.md`（编号 I1、I2…，写条款、位置、改法、级别）。之后的验收只判定：
   - `issues.md` 中未关闭的项是否按改法修好；
   - 本轮 diff **改动行**上引入的新问题；
   - 结构条款（R1、R2、R7～R11、R14、R15、R18）是否被本轮改坏。
2. 没改过的行上新发现的文字级问题（注释、文档注释、日志措辞，涉及 R3、R5、R6、R12、R13、R16）**不计入结论**，写进验收报告的“遗留建议”，交付时一并列给用户。
3. 某条款已在完整验收中 PASS，且相关文件本轮没有结构改动时，直接写“沿用第 X 轮”。
4. **文字级上限**：连续两轮只剩文字级不通过时，不再开新轮：调度者按快速路径照改，核对式确认后交付，其余意见列为遗留建议。

## 耗时纪律（调度者与所有子代理都必须遵守）

总耗时 ≈ 每步等待模型的时间 × 工具步数 × 轮数，要压的是**步数**和**轮数**：

- **并行发起**：互不依赖的 Read/Grep 在同一回合一次性发出。
- **一轮只验证一次**：编译、单测、check-readability、项目守卫统一用 `readability-verify.mjs` 一次跑完，只读它打印的摘要；改动过程中不要反复编译。
- **Shell 合并**：能用 Read/Grep 完成的不调用 Shell；必须用 Shell 时把多条命令合并成一次。
- **断点目录可能对 Glob 不可见**（被 `.gitignore` 忽略时）：已知文件直接用完整路径 Read/Grep；列目录用 Shell（Windows `cmd /c "dir /b ..."`，其它系统 `ls`），不能用 Glob 判断“没有报告”。
- **Read 与 Shell 不并行**：读取 Shell 刚写出的文件，必须等 Shell 返回后再 Read。

## Token 纪律

- **一个会话只处理一个目标类**。目标类交付后，下一个类在新会话里执行 `/readability-loop`。
- **子代理不复用**：拆分方和验收方每次都新开，禁止 `resume`。上下文只靠断点文件传递。
- **只传路径，不传正文**：给子代理的提示词只写文件路径和本轮要修的条款或 issues 编号。调度者自己只读报告最后的“结论”行，以及不通过条款表。
- **子代理分批**：一个拆分子代理最多处理 4 个文件或 20 个待改项。超过时按文件分批，依次启动多个拆分子代理；上一批的 todo 勾选完再启动下一批。
- **读取范围**：子代理只完整阅读本批范围文件。范围外的类只用 Grep 定位到具体行，禁止通读。
- **大文件由调度者先测绘**：范围文件代码行超过 600 行（R1 上限的 2 倍）时，调度者在开局用 Grep 工具（不用 Shell）做两件事，写进 `<断点目录>/refs-summary.md`：① 一次正则批量查询范围外对目标类群符号的引用，整理出“必须保持不变的对外面”（类型、入口方法、各自调用方）；② 按行号取声明清单（类、方法、字段），按职责起草拆分草案。拆分方直接使用，禁止重新扫描引用，禁止自写脚本找引用。
- **结构先行，文字后补（同一轮内分批）**：首轮有 R1 或 R4 时，第 1 批只做结构项（R1 拆文件、R4 拆方法、R7 内联、R2/R14 等）和新类的类说明；R16 成员说明、R5 步骤注释等文字项留到后续批次，在拆好的小文件上补。各批仍属同一轮，最后一批才跑 verify、写报告。不要把文字项推迟到下一轮，多一轮就多一次验收。
- **中止产物作废**：子代理被中止或熔断后，断点目录中不属于“断点文件”表的文件（临时脚本、扫描结果等）一律视为作废；调度者在 `refs-summary.md` 或下一批提示词里写明，新子代理不读取。
- **命令输出写文件**：其它命令一律重定向到 `<断点目录>/<名称>.txt`，再用 Grep 取关键行。
- **用量守护熔断即停**：工具或子代理被 token 守护（如 token-guard hook）拒绝时，不再启动新子代理，只按“断点文件”更新 `loop-state.md`（工具也被拒绝时跳过），然后进入第 3 步交接。
- **口径冻结**：循环开始后不修改 `rubric.md` 和项目规则。用户中途提出新要求时，先结束当前循环（写清当前状态），优先写成通用条款补进 `rubric.md`（只与该项目有关的写进项目已有规则文件），再在**新会话**里重新开始。

## 0. 开局（调度者自己做，不启动子代理）

1. **从项目规则提取守卫参数**：在已加载的项目规则中找“守卫/guard 脚本”要求（例如“修改绘制对象时运行 `node tools/check-xxx-guard.mjs`”）。范围命中其条件时，把每条写成 `--guard "<命令>"` 记进 `loop-state.md` 的“守卫参数”；没有就写“无”。不要为此另读文件，也不要求用户建配置。
2. **有 `loop-state.md` 时**（直接 Read `<断点目录>/loop-state.md`，读不到再走第 3 条）：
   - 按其中的“阶段/下一步”续跑，不重新拍基线，不跑 start 检查；
   - 阶段为“编辑”时，用一次 Grep 核对 todo 中 `[ ]` 项的“改法”文本是否已经出现在源码里，已出现的直接勾选；
   - 跳到对应步骤：待办/编辑 → 1.1，校验/报告 → 1.1（拆分方只做剩余阶段）或快速路径，验收 → 1.2，判定 → 1.3。
3. **没有 `loop-state.md` 时**（新类，或旧版本循环留下的目录）：
   - 确定范围：目标类文件，加上同一次拆分产生的类（同包或子包），写成文件列表；
   - 用**一次** Shell 调用把断点目录列表、`git status --porcelain -- <范围目录>`、`node <技能目录>/scripts/check-readability.mjs <范围文件>` 的输出写进 `<断点目录>/start.txt`，等 Shell 返回后再 Read；
   - 范围内有与本任务无关的未提交改动时，先停下来问用户。来自本类之前几轮循环的改动不算无关；
   - 旧目录按最新文件推导阶段：最新是 `round-<N>-refactor.md` 且无对应 review → 验收；最新是 FAIL 的 `round-<N>-review.md` → 第 N+1 轮“待办”；有 `r<N+1>-*` 中间文件但没有 `round-<N+1>-refactor.md` → 第 N+1 轮“编辑”；
   - 把最近一份 FAIL 验收报告的不通过行写进 `issues.md`，再写 `loop-state.md`；
   - start.txt 显示范围文件超过 600 代码行时，按“Token 纪律”的“大文件由调度者先测绘”写 `refs-summary.md`，再启动拆分方。
4. **累计轮次上限**：累计轮次达到“用户确认的累计轮次上限”（默认 6）时，先把 `issues.md` 中未关闭的项列给用户，由用户选择“继续修哪些项 / 接受现状交付 / 调整 rubric”。用户同意继续时，把新上限写进 `loop-state.md`。
5. 本会话内的轮数从 1 开始重新计数。

## 1. 循环（每个会话最多 2 轮；快速路径不占轮数，但计入累计轮次）

没有子代理能力的环境（例如部分 CLI）：拆分方与验收方分别在两个**新会话**中执行（由用户开启），调度者在当前会话只维护断点文件。禁止同一会话里自己改完再自己验收。

### 1.1 拆分子代理（新开，通用型子代理，前台执行）

```text
你是可读性重构的拆分方。仓库：<项目根目录绝对路径>
先阅读并执行 <readability-refactor 技能目录>/SKILL.md，口径是 <技能目录>/rubric.md 加项目规则；断点目录：<断点目录绝对路径>。
目标类：<类名>；范围文件：<文件列表>；本批文件：<分批时写本批；不分批写“同范围”>。
当前轮次：<N>（累计第 <N> 轮；N ≥ 2 时不要重读项目规则要求的首轮规范技能）。
本轮要修：<第 1 轮写“全部”；之后写 issues.md 中的未关闭编号，如 I7、I8>。问题清单：<断点目录>/issues.md。
引用与拆分草案：<断点目录>/refs-summary.md（存在时直接使用，禁止重新扫描引用；没有就写“无”）。本批只做：<结构项 / 文字项 / 全部>。
待办：<断点目录>/r<N>-todo.md。不存在时先列全本批待改项再动手；存在时只做 [ ] 项，动手前确认源码里还没有新文本；每改完一个文件立刻勾选该文件的项。
本批需要完成到：<编辑 / 编辑+校验+报告>。校验命令：node <技能目录>/scripts/readability-verify.mjs，必须带上守卫参数：<loop-state 中的守卫参数或“无”>；本轮有结构改动时不得带 --skip-test 和 --skip-guard。
完成后回复只给：todo 中 [ ] 剩余数、报告路径（如已写）、readability-verify 摘要的最后 4 行（如已跑）。
```

### 1.2 验收子代理（新开，通用型子代理，前台执行）

- 如果可选模型中有与拆分方不同的模型，验收方使用不同模型；调用因额度不足失败时，立即改用默认模型重试一次，并在提示词中要求“以挑问题为目标”。
- 验收模式三选一：
  - **完整验收**：第 1 轮、有结构改动的轮次、最后确认轮。判定 R1～R18，但文字级条款只按收敛规则判定。
  - **增量验收**：中间轮，只判定 `issues.md` 未关闭项和本轮 diff 改到的文件所涉及的条款。
  - **核对式确认**：快速路径之后。只核对指定 issues 是否按改法修好，以及本轮 diff 是否只改了注释、文档注释、日志文案。

```text
你是可读性重构的验收方，只读，禁止修改源码、技能或文档。仓库：<项目根目录绝对路径>
先阅读并执行 <readability-review 技能目录>/SKILL.md，口径是 <技能目录>/rubric.md 加项目规则；断点目录：<断点目录绝对路径>；守卫参数：<同上>。
目标类：<类名>；范围文件：<文件列表>；当前轮次：<N>；验收模式：<完整 / 增量 / 核对式：I…>。
基线：<断点目录>/baseline.md；问题清单：issues.md；本轮改动报告：round-<N>-refactor.md；上一轮验收：<路径或“无”>。
写 <断点目录>/round-<N>-review.md。回复只给：结论（PASS/FAIL）、不通过条款编号、不通过项是否全部为“文字级”。
```

### 1.3 判定

调度者先把本次验收的不通过行追加进 `issues.md`，并把已修复的项标为“已关闭”，再按下表处理：

| 验收结果 | 处理 |
|---|---|
| 完整验收或核对式确认 PASS | 进入第 2 步交付 |
| 增量验收 PASS | 做一次完整验收作为确认轮 |
| FAIL，且不通过项全部为文字级 | 走快速路径 |
| FAIL，含结构项，本会话还没用完 2 轮 | 轮次 +1，阶段写“待办”，回到 1.1 |
| 本会话已用完 2 轮，或同一 issue 连续两轮未关闭 | 停止，进入第 3 步交接 |

**快速路径**（文字级照改，调度者自己做，不启动拆分方）：

1. 轮次 +1，把验收报告里可照抄的改法逐项写进 `r<N>-todo.md`，阶段改为“编辑”；
2. 每项只 Read 定位行前后约 10 行，照改；每改完一个文件勾选对应项；
3. 跑一次 `readability-verify.mjs --name <类名> --round <N> ... -- <范围>`。只有上次结构改动之后的 verify 已经完整通过时，才可以加 `--skip-test --skip-guard`；
4. 写不超过 30 行的 `round-<N>-refactor.md`：改了哪些 issue、在哪个文件、verify 摘要；
5. 启动验收方做**核对式确认**。PASS 即交付；FAIL 时按上表处理，同一 issue 第二次未关闭就交接。

## 2. 交付（PASS）

把 `loop-state.md` 的阶段改为“交付”，然后向用户汇报，控制在一屏以内：

- 改了哪些文件，拆分前后的代码行数；
- 改后的入口调用树（从最后一份完整验收报告中摘录）；
- 每一轮的不通过条款及修复方式，一句话一条；
- 编译、check-readability、项目守卫、单测的命令与结果（摘自 `r<N>-verify-summary.txt`）；
- 验收报告中的“遗留建议”和“建议补充条款”（如有），请用户决定是否处理；采纳的条款优先写成通用条款补进 `rubric.md`。

## 3. 交接（未通过或熔断）

把 `loop-state.md` 的阶段和下一步改成新会话照做就能继续的一句话，然后向用户说明：

- 卡在哪几个 issue，拆分方与验收方各自的理由；
- 需要用户裁决的口径问题（用选项提问）；
- 下一步：用户裁决后（熔断时先解除用量守护），在**新会话**执行 `/readability-loop <类名>`，开局会读取 `loop-state.md` 自动续跑。
