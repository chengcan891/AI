# Git 合并与功能回归

按用户指定的分支、基线和合并方式执行。遵循目标仓库的 AGENTS.md、文件读取约定和编译授权。用户只要求判断时做只读检查，接手合并时完成已授权范围内的冲突处理和回归核对。

## 确认当前合并状态

- 读取 `git status --short`、未合并文件和当前提交，确认是在合并、重放还是挑拣提交，并分清用户已有的改动与本轮结果。正在 rebase 时用 `REBASE_HEAD` 定位正在重放的原提交。查看历史时记录两条线的原始提交点和共同基线，供最终对照。
- 对冲突文件查看 index 的 stage 1、2、3 和实际分支来源。普通 merge 中 stage 2 是当前分支，stage 3 是合入方。rebase 中 stage 2 是新基线及已重放的提交，stage 3 是正在重放的提交。IDE 的左右和 Yours/Theirs 以窗口注明的提交来源为准。
- 识别本轮的功能改动、明确移除项及依赖关系。查看本轮整个差异，包括 Git 已自动合并的文件。合并工具没有标红的改动也可能造成行为回退。

## 逐处合并，保护两边的行为

- 对双方有修改的区域，以共同基线对照两边各自引入的行为。按入口、调用链、配置、默认值、结果和失败处理逐项核对，保留用户要求继承的行为。整文件选择一侧前，确认另一侧的有效改动已经包含、另有实现或已明确移除。
- **一侧删除、另一侧修改时，先查修改再决定怎么处理。** 核对删除原因，比较保留方相对基线新增或改变的行为，并追查现存调用方、注册入口、资源及依赖。若有替代实现，确认调用确实能到达它，把另一侧新增且仍有用的逻辑迁过去，再删除旧实现。若没有替代且仍被调用，保留该功能及其完整调用链。只有明确属于预期移除，或能证实已无用途且无遗漏行为时，才接受删除。包名或 import 迁移本身可随旧实现一同移除。
- 对接口、模块或实现迁移，核对声明、真实调用、运行时注册、构建依赖和关联资源。特别核对错误码、服务端提示、回调线程与结果、数据兼容和设备协议参数。确认旧实现上的改动已落到新的生效位置。
- 二进制依赖无法按行合并。对照两侧版本的公开接口、调用方、必要的 ABI 和已知行为变化。选用能支持合并后功能的一份。只凭文件更新时间或体积无法确定时，查来源或明确记录需要用新的依赖构建结果确认。
- 整条提交只在确认其所有有效改动均已覆盖或明确舍弃时才跳过。保留用户工作区和已做的冲突处理。有正在编辑的 IDE 合并缓冲区时，通过 IDE 工具协作或等编辑保存后再操作同一文件。

## 每轮结束前检查

- 对照原提交与本轮实际差异，逐项记录受影响功能在合并后的去向和检查结果。至少追通关键入口到最终行为，核对被删符号的残留引用、自动合并引入的重复或失效声明、依赖注册与调用签名。对触及的默认行为、错误分支、状态更新及数据迁移做定向检查。
- 合并 Gradle、模块迁移或依赖精简时，按最终源码检查受影响模块的新增引用和已有 import。核对依赖删改后类路径是否仍覆盖这些符号，包括原依赖包带入的库。补齐仍在使用的直接依赖，并检查对外签名、父类或接口需要的依赖是否向调用模块暴露。
- 一侧改过方法签名、另一侧改过方法体或新增分支时，按最终方法签名复查所有返回、提前退出和回调路径，并核对调用端。返回类型由 `Boolean` 改为 `Result<T>` 时，新增失败分支沿用目标分支的失败结果构造，保留退出前后的状态更新顺序。
- 用 `git diff --name-only --diff-filter=U` 确认没有未解决项，并对合并结果运行 `git diff --cached --check`。核对暂存内容只包含本轮预期改动。IDE 已暂存的文件可直接继续，手工编辑后仅暂存已核对的路径。
- 在仓库允许且已授权时运行相关构建、测试或实机检查。仅有静态证据时明确记录“源码已核对”和还需运行确认的功能。当前轮发现遗漏，要在继续前补齐。是否执行 `rebase --continue`、完成合并提交或推送，按用户授权范围处理。

## 全部提交合并后的完整回归

- 全部提交合并后，安排独立验收子任务。调用本技能即视为授权只读验收子任务（不授权编译、推送或改历史，这些仍需单独确认）。交接仓库路径、合并前双方提交点、目标提交、预期移除项和验收要求。子任务只读核对最终差异、调用链和易丢失的行为，作为独立证据给出通过或问题清单。主任务修复已证实的问题并复核后再完成。
- **何时重新验收**：每次 HEAD 变化后都要重新验收，包括 rebase、merge、force push 前的改写、拉取新的上游提交后再次合并或变基。沿用旧 HEAD 的验收结论不算通过。
- **验收前先核对基线是否最新**：先 `git fetch`，再比较 `git merge-base HEAD origin/<目标分支>` 与 `git rev-parse origin/<目标分支>`。不相等说明基线已过期，应先变基到最新上游再验收；不得把“变基成功”直接等同于“已合并最新代码”。
- **什么算独立**：执行合并或变基的同一 agent、以及由它分叉出去的子任务，都不算独立验收，只能作为自检。独立验收必须是新开的 subagent（`generalPurpose` 或 `explore`），只读，不接收执行过程的结论，只接收仓库路径、提交点和检查清单。
- **验收失败或中止**（如子任务 Aborted、token 熔断、超时）：不得跳过。先重试一次，仍失败则在交付中明确写“独立验收未完成”，并列出已自检的范围和未覆盖的风险，不得写成“已通过”。
- 无法安排子任务时，明确说明原因并自行完成同等范围的检查，同时标注为“自检，非独立验收”。

- 从合并前记录的两侧提交点出发，对照原始提交清单、合并结果和用户明确要求的移除项。rebase 可用 `git range-diff` 辅助找漏放或异常变化的提交，再核对最终代码和实际调用。不要把提交条数相等或冲突清零当作功能完整的证据。
- 逐项检查双方新增和变更的功能，以及被共享代码影响的原有能力。覆盖正常入口、成功与失败分支、配置与恢复、替换后的真实调用；核对后续提交有没有重新引入已删依赖或覆盖此前的合并结果。按仓库和用户授权执行现有测试及关键场景回归。
- **最终编译**：全部重放或合并完成后，在仓库规则允许且用户已授权时直接编译一次。优先选择能覆盖受影响模块及其调用方的仓库标准任务。Android 项目通常使用对应 app 变体的编译或 assemble 任务，让 Gradle 解析模块依赖并编译 Kotlin、Java。Gradle Sync 和静态核对只能单独记录。
- 编译失败时从第一批实际报错定位并修复，尤其关注缺依赖、签名不匹配和自动合并引入的类型错误。在已授权范围内复编确认。仓库要求单独确认且用户尚未授权时，完成静态检查，按仓库要求请求编译确认。用户明确自行编译时，记录编译待验证。
- **验收反馈**：最终编译、测试或实机回归发现合并引起的问题时，在同一轮修复代码并定位原检查为何漏检。把可复用的检查补到技能中最早能发现该问题的环节；已有检查覆盖时，补充具体核对动作或证据。合并特有的教训更新本技能，项目特有的规则放到相应项目约定。修改后校验技能，并在交付时说明补了什么以及复验结果。
- 汇报已验证的功能、预期移除项、迁移位置和待验证项。遇到失效入口、未迁移行为或验证失败，先修复或说明具体阻塞，避免把部分验证写成完整通过。
- 汇报必须包含一行“验收方式”：`独立验收通过` / `独立验收未完成（原因）` / `仅自检`，以及对应的 HEAD 提交号。

## 每次使用后的复盘

每次使用本技能结束前，在交付中加一段“技能复盘”，回答三个问题，并据此更新本技能：

1. 本次有没有因为步骤表述不清而偏离（例如漏做验收、误判独立性、把失败写成通过）？如果有，把对应规则改得可执行，写清触发条件、判定标准和失败处理。
2. 本次有没有发现新的回归类型？如果有，补到最早能发现它的检查环节，并写明具体核对动作。
3. 技能修改后，用 `git diff` 或重新读取确认格式没有破坏，并在复盘里说明改了什么。

复盘只记录通用经验，项目特有的规则放到对应项目约定中。
