# 可读性重构：拆分方

## 路径约定

- `<循环技能目录>`：同级目录 `../readability-loop/`（调度者会在提示词里给出绝对路径）。通用口径 `<循环技能目录>/rubric.md`，脚本在 `<循环技能目录>/scripts/`。
- 项目规则：宿主自动加载的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/` 等。其中写到的强制规范技能、对外接口、时序不变量、守卫脚本作为 rubric 的补充生效，冲突时以项目规则为准。项目不需要为本循环另建配置。
- `<断点目录>`：调度者给出的绝对路径（`build/readability-loop/<类名>/`，项目没有 `build/` 时为 `.readability-loop/<类名>/`）。

## 角色边界

- 只负责修改代码并输出“改动报告”，**不自行判定是否通过**，是否通过由 `readability-review` 决定。
- 每次只处理一个目标：一个类，或一个入口类及其拆出的类群。
- 唯一口径是通用 rubric 加项目规则。项目规范要求“多阶段必须拆分方法”与 rubric R7、R8 冲突时，以 R7、R8 为准：不足以独立成方法的阶段保留在原方法内，用步骤注释标出。

## 输入

1. 目标类路径（入口类）。
2. 问题清单 `<断点目录>/issues.md` 中调度者指定的未关闭编号（第一轮为空）。有清单时，**只修清单里的问题**，不重新设计已通过的部分。
3. **同类清扫**：只在本批文件内查找与清单项同一模式的位置（非加密 Grep；加密则在已 Read 的片段里搜），**先把找到的位置写进 todo，再动手改**。清单项以外的其它问题不要改。
4. 本批文件与待办清单 `r<N>-todo.md`（见下节）。

## 待办清单与断点

熔断随时可能发生，进度必须边改边落盘：

1. **先列后改，只列本批**：`r<N>-todo.md` 不存在时，只把**本批**待改项写进去就开工，不要为了“完美 todo”先通读全部范围文件、细化后续批次。有 `refs-summary.md` 时直接按其中的拆分草案与符号名写，定位文本用 Grep 取，不先整文件 Read。后续批次每个计划文件只写一行占位 `- [ ] 第 K 批：<新文件> ｜ 待展开`，到该批开始时再展开。一项一行：
   `- [ ] 文件:方法 ｜ 定位文本（可唯一定位的原文片段） ｜ 改法（文字级写出新文本；结构改动写清目标位置）`
   最后另起两项 `- [ ] 校验` 和 `- [ ] 报告`。
2. **按文件改，按文件勾**：一个文件的项全部改完，立刻把这些项改成 `[x]`，再处理下一个文件。
   - **提取成对落盘**：每提取一个单元（新文件），紧接着删除主类里的旧定义、改为调用新类，两步都完成后一起勾选，再做下一个单元。不要先把几个新文件都建好、最后统一清理主类，否则中断时会留下“重复声明、编不过”的中间态。
3. **续跑**：todo 已存在时，只做 `[ ]` 项；动手前用 Grep 确认源码里还没有新文本，已有就直接勾选。不要重做 `[x]` 项，也不要再全量清扫。
4. **校验与报告也是待办项**：verify 通过后勾选 `校验`，写完改动报告后勾选 `报告`。
5. 被用量守护（如 token-guard）拦截时立即停止，不要试图补写报告；已勾选的进度就是断点。

## 耗时纪律

### 加密源码环境

若对已知符号 Grep 源码得 0 命中，视为加密盘：

- **禁止**对范围源码 Grep/rg；只用 `Read` 分段读取。
- 单文件最多 3 段整读，每段参数不重复；之后只按行号局部 Read。
- `refs-summary.md` 已有则直接用，禁止再扫引用。
- 提示词或 `loop-state` 写明“加密环境：是”时，本节优先于下文所有“用 Grep 定位”的句子。

- 互不依赖的 Read（非加密时含 Grep）在同一回合一次性并行发出；非加密时范围文件可在第一个工作回合并行读取，加密时按“最多 3 段”规则读，禁止为并行而重复读同一段。
- 改动过程中不要反复编译。分批时，**非最后一批的结构批次**在本批 todo 全部勾选后跑一次批内编译检查（只编译，不跑单测、check-readability、守卫）：
  `node <循环技能目录>/scripts/readability-verify.mjs --name <类名> --round <N> --batch <K> --compile-only -- <范围文件或目录>`
  结果写 `r<N>-b<K>-compile.txt`，编译失败当批修好再返回；它不算“校验”，不勾选 `校验`。只改文字的批次不跑。
- 本轮所有修改完成后（分批时为最后一批），只调用一次完整验证（在项目根目录）：
  `node <循环技能目录>/scripts/readability-verify.mjs --name <类名> --round <N> [--tests <过滤>] [--task <额外构建参数>] [--guard "<守卫命令>"] -- <范围文件或目录>`
  构建系统自动识别（Gradle 按范围所在模块推导编译与单测任务，Node/Maven/Cargo/Go/dotnet/Python 用常规命令）；识别不准时用 `--build "<命令>"`、`--test "<命令>"` 覆盖。调度者提示词里给出的 `--guard` 必须照带。它一次完成构建与单测，再跑 check-readability 和守卫，摘要写入 `r<N>-verify-summary.txt`。只有摘要报告失败时才去 Grep 对应日志，修完再整体重跑一次。
- 本轮只改注释、文档注释、日志文案，**且**上次结构改动之后的 verify 已经完整通过时，才加 `--skip-test`，编译仍然要跑；同样条件下本轮不涉及守卫所保护的对象时加 `--skip-guard`。有迁移、拆分、合并、改签名等结构改动时，两个参数都不得加。
- 能用 Read/Grep 的不用 Shell；加密环境下 Grep 源码无效，不要用 Shell `findstr`/`rg` 代替。必须用 Shell 时合并成一次。断点目录被 `.gitignore` 忽略时对 Glob 不可见，查报告文件用 Shell 列目录。
- **提取与编译边界**：每提取一个单元必须当时完成“新建 + 主类删旧定义 + 委托”，再 `--compile-only`；未通过批内编译前不要开始下一批文件。不要把多个新文件都建完再统一改主类。
- **R2**：按草案预估或首轮拆完后合计代码行仍高于基线 110%、且再合并会破 R1 时，停止拆合，在入口类类说明写入例外原因与退出条件（文案按验收/issues 的“怎么改”），把精力留给真正的结构 FAIL。

## Token 纪律

- 每轮都是新开的子代理，上下文只来自磁盘文件。`baseline.md` 已存在时跳过“拍基线”。
- 上一轮验收报告只读“逐条结论”里的不通过行，以及“上一轮不通过项复核”，不要通读全文。
- 只完整阅读本批范围文件。范围外：非加密用 Grep 定位；加密用最短局部 Read；禁止通读。
- 编译、单测、脚本一律写文件：`<命令> > <断点目录>/<名称>.txt 2>&1`，再用 Grep 取关键行。日志文件保留，供验收方复用。
- 改动报告不超过 80 行。调用树和调用序列对照只在第 1 轮完整写出；之后各轮只写“本轮改了什么、在哪个文件”，以及变化的那部分调用树。
- 全仓库搜索用一次 `rg` 批量查询多个名称，并排除构建产物目录，不要逐个名称反复搜索。
- `<断点目录>/refs-summary.md` 存在时，直接使用其中的对外面和拆分草案，不再扫描引用、不自写脚本找引用；只需核对个别符号时用 Grep 工具定位到行。断点目录中不在约定文件之列的文件（中止残留的临时脚本、扫描结果）不读取。
- 超过 600 行的范围文件按行段 Read（每段不超过 400 行，**全文件最多 3 段**），每段只读一次，之后只按需读局部片段；禁止反复整文件读取，禁止相同参数重读。
- 分批的第 2 批起，主类已被前批改过，**不再整文件 Read**：按本批要搬的符号名一次 Grep 取行号，再按行段 Read 这些方法和字段；新建文件只读前批产出的类声明与签名行。
- 调度者指定“本批只做结构项”时，只改结构并给新类写类说明，搬移的代码原样保留已有注释；R16、R5 等文字项保持 `[ ]`，留给后续批次。

## 执行步骤

1. **读口径**：读 `rubric.md`。
   - 累计第 1 轮（或新范围的首轮）：另外读项目规则中标为“类/方法级工作前必须读取”的规范技能，以及“修改 X 前使用 Y”中被本次范围命中的技能（与 rubric 同一回合并行读取）。
   - 累计第 2 轮起：**不再重读这些规范**。rubric 已经包含它们的验收要求；只有本轮新增类或命中项目规则中的条件时才按需读对应技能。
2. **拍基线（只在第一轮执行）**：
   - 记录 `git rev-parse HEAD` 作为基线提交；
   - 统计目标类群的代码行数和物理行数（R2 要用）；
   - 写下入口方法的实际调用序列（R15 要用），以及对外签名清单；
   - 写入 `<断点目录>/baseline.md`。
3. **画现状调用树**：从入口方法展开到第 3 层，标出空壳转发（R7）、超过 3 层的链路（R8）、双通道数据（R9）、重复状态（R10）、散落的功能（R11）。
4. **按以下优先级修改**（先结构，后注释）：
   1. 合并与内联：去掉空壳方法和转发类，压低调用深度；
   2. 按功能聚合：把散落的同一功能收拢到一个类；
   3. 按功能分包（R18）：满足触发条件时分子包，入口类留在父包，同步迁移测试包路径、导入语句和文档全限定名；不分包时在报告里写明原因；
   4. 状态唯一：重复状态只保留一个持有者，其他类改为通过参数获取；
   5. 数据流显式：去掉双通道，工作区字段标注“谁写/谁读”，跨类方法不用隐式接收者作用域；
   6. 删除无用代码：逐个全仓库搜索引用，附证据；
   7. 补类说明三段式（职责/不负责/使用步骤），补方法文档注释与步骤注释；
   8. 按 R12 补日志：生命周期和状态变化打日志，高频路径不打无条件日志。
5. **自检、编译与守卫（一次调用）**：todo 中的改动项全部勾选后，运行 `readability-verify.mjs`，修到摘要为“结果：全部通过”再勾选 `校验`；check-readability 的 `WARN` 项在报告中逐条说明。改动跨模块时用 `--task` 追加范围外模块的构建参数。分批时只有调度者指定“编辑+校验+报告”的那一批才跑完整 verify；其它结构批次只跑上文的批内编译检查。
6. **写改动报告**到 `<断点目录>/round-<N>-refactor.md`，覆盖本轮 todo 的全部项（包括之前批次或被中断的会话已完成的项，可按文件汇总），写完勾选 `报告`。

## 改动报告模板

```text
# 第 N 轮改动报告：<类名>
基线提交：<hash>    代码行数：改前 X / 改后 Y（Y/X = Z%）    物理行数：改前 / 改后

## 修复的上一轮不通过项
- I3（R8）：…（改了什么，在哪个文件）

## 结构变化
- 合并/内联：A.foo() 内联进 B.bar() 步骤3
- 新增/删除/改名的类：…
- 分包（R18）：子包 → 类列表，或不分包原因

## 入口调用树（改后，展开到第 3 层）
<入口方法>
├─ 步骤1 …
└─ …

## 调用序列对照（R15）
| 序号 | 改前 | 改后 |

## 删除清单（R14）
| 方法/字段 | 引用搜索命令 | 结果 |

## 校验（摘自 r<N>-verify-summary.txt）
- readability-verify：<完整命令> → 全部通过/存在失败
- check-readability：FAIL 0 / WARN n（逐条说明）
- 单测、项目守卫跳过时写明原因
```

## 禁止事项

- 禁止为了满足行数指标把代码挪到新的空壳类里（会被 R2、R7 判不通过）。
- 禁止修改业务行为、处理顺序、线程边界，以及项目规则写明的时序不变量。
- 禁止在报告里声称“已验收通过”。
